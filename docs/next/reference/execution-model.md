# 执行模型：请求、任务与回执

Action 是宿主公开的具名操作契约，包含输入、输出、说明和 effect。运行时目录由该宿主实际注册的能力构成。`read`、`write`、`destructive` 是接口分类，不是对外部网络、缓存、自动确认或可撤回性的统一保证。输入校验、权限、宿主前置和具体影响以目标设备的实时描述为准。

## 一次请求可能经历的阶段

一个请求可以在接收、执行、事务提交、后续投影和响应交付之间经历不同阶段。有些 Action 直接返回结果，有些返回持久任务；收到任务表示受理，并不证明任务已经完成。任务状态、阶段、事件与回执可继续变化，成功状态也应结合领域回执和必要的回读理解。

- **任务**负责持久执行与恢复，具有任务 ID、状态和可观察的进度。等待是有界观察；等待超时不会自动取消任务。
- **事件**记录发生过的变化，可用于通知或触发后续；事件与数据库事务回执不是同一个东西，收到事件不意味着每个投影和消费者都已更新。
- **领域回执**按各领域契约证明提交或结果；通用过程观察说明调用阶段，有保留期限，不能代替持久提交证明。
- **取消**是请求停止，可能发生在部分效果或提交之后。取消响应不证明已提交的数据被撤销；撤回需要该领域提供可用的撤回协议与冲突检查。

## 预览、冲突和重试

有些写入先生成预览，再在事实仍匹配时提交；预览不是提交，也不是用户授权。SQL 写入用预览和冲突核验，提交回执与数据同事务保存；可用相应撤回入口预览并处理后续冲突。媒体绑定、合并、下载删除与文件操作各有自己的预览、确认和恢复规则，不可套用同一个流程。

`not_delivered` 表示本次没有找到可交付连接，不证明之前同类请求未执行。`outcome_unknown` 表示请求可能已到达或提交但结果未取回，并不等于失败或回滚。应保留目标设备、调用来源、原请求键及输入，先查对应任务、领域回执和过程；仅在该领域明确提供幂等重试时按原契约恢复。不要因为未知就换新键重新执行写操作。

SQL 的持久回执以原 write previewId 或 undo requestId 查询；`unknown` 仍可能是在途、来源不符或无记录。`committed` 证明事务提交，提交后的通知是否完成另看回执状态。只读目录或文件数据可重新获取，但不完整的传输不能冒充完整结果。

常见误解：**Action 返回**不等于后台任务结束；**断线**不等于未提交；**已取消**不等于撤销已发生的效果；**短期诊断里找不到**不证明历史操作不存在。
