# Mesh 鲁棒性核查：2026-10-27

## 范围

产品范围由用户确认：内网设备直接互通；对应设备具有可达公网地址时也可直连。
不要求自动 NAT 穿透或托管中继，不将这两项未实现视为鲁棒性缺陷。

本轮只核查后端、传输边界和数据库事实；撤回尚未提交的四个元数据浏览页面。
不从单独的裸视频 URL 播放测试推断正常弹幕播放是否失败，也不为该测试新增
弹幕获取入口。正常播放仍在开播准备阶段取得资源包，已确认分集 ID 可用于自动
获取、持久保存弹幕，刮削本身不必提前下载。

## 三条链路

| 链路 | 实现 | 代理策略 |
| --- | --- | --- |
| 公网协调服务 | `MeshCoordinator` 的 HTTPS；签发/续期身份、同步设备、登记和查询地址 | 使用应用或系统出网代理；公网 TLS 仍需验证 |
| 对端 RPC 和文件数据 | Rust `TcpStream::connect` + TLS 1.3 双向认证 | 应用 HTTP 代理不参与；实际路由仍受操作系统 VPN/TUN 等影响 |
| 播放器读取本机转接服务 | 接收端按需监听 `127.0.0.1`，支持 HEAD、Range，再向源节点读取数据 | 回环必须 DIRECT，不能交给出网代理 |

设备 deviceId 来自公钥，候选 IP 是可替换的寻址线索。候选排序、地址登记、
本机端口号都不替代 TLS 中的设备身份验证。即使旧 IP 被分配给另一台设备，
它也不能仅凭占用该 IP 通过原设备的认证。

## 已定位并修复的缺陷

1. 富元数据超过旧目录页的单记录大小上限，整库同步失败；接收端又把同步失败
   当作设备离线。已通过字节分块、不可变 publication、保留旧目录与独立认证
   可达性探测拆开这些状态。不是所有历史 offline 都是地址不可达。
2. 普通 RPC 大响应超过帧上限。通过 continuation 获取结果而不重复原操作。
3. `AppHttpProxy.findProxy` 在配置手动出网代理后，也把回环交给代理；原来只有
   协调服务和部分播放器调用点单独绕过。统一在该策略入口保持 localhost、
   IPv4 127/8、IPv6 ::1 与 IPv4-mapped loopback 直连。没有把所有私网地址
   一律设为直连，以免更改局域网媒体服务的已有代理选择。
4. `playback.open` 对稳定 `mesh:///episode` 定位符套用普通网络 URL 的 host
   要求。允许合法单剧集定位符进入现有正常解析器，拒绝带 host、多段路径、
   query 或 fragment 的不合法输入。不增加另一套弹幕播放流程。

## 仍然存在的结构限制

### 寻址范围与失败语义

协调服务只提供身份和地址控制面，设备必须有当前网络实际可达的候选地址和
监听端口。内网直连和可达公网设备直连属于既定范围。网络自身禁止设备互访时，
应准确报告连接不可达，不把这种情况表述为需要产品增加自动穿透或中继。
下面的鲁棒性问题只讨论既定范围内的地址恢复、代理边界及有界失败。

### 地址变化的恢复速度没有统一保证

现有代码有成功路由缓存、局域网发现、错开 250 ms 的候选尝试和失败后重新查询。
但常规地址上报随至少 900 秒的心跳，UDP 发现每 30 秒广播；本轮未发现专门
响应操作系统网络变化的统一地址重新上报机制。广播被隔离时，网络切换后的恢复
不能仅凭这些机制保证足够快。需要网络变化触发的去抖重新枚举/上报，并在服务端
限额内提供有界恢复。

### 虚拟网卡候选需要保持明确的选择策略

自动 LAN 上报排除 utun、tun、wg、tailscale、容器与虚拟网卡，避免把无关地址
当作可用 LAN。这同时意味着合法 overlay 也可能需要显式填写候选。不能简单
放开所有虚拟接口；应区分物理 LAN、用户选择的 overlay 和排除接口。

### 媒体传输需要单独的时限和资源控制

当前 Rust 每次 send 建立 TCP/TLS，连接与握手各有 10 秒时限，但响应读取共用
最长 3600 秒的通用调用期限。文件转接循环通过 RPC 按块读取。因此还需要专门
验证半开连接、媒体块超时、用户取消及高延迟吞吐，不能把长任务的等待策略当作
媒体读取策略。后续应为媒体读取设置独立时限、取消与受限恢复，再评估连接复用。
不得因为读取重试而重放结果不确定的写操作。

## 处理优先级

1. 保持代理边界一致、目录失败与设备可达性分离，错误暴露实际阶段。
2. 在内网直连范围加网络切换、旧 IP/端口及半开连接的故障注入，要求有界失败
   与恢复，避免无限加载；兼顾有公网地址的可达设备。
3. 为媒体读取增加独立取消/超时与资源控制，测高延迟和 seek 下的吞吐。
4. 保持设备身份与地址分离；地址变化时重新发现与认证，公网候选仍走同一套
   双向 TLS。无需在本轮增加穿透或中继，也不为此改动产品架构。

## 证据与验证边界

- 本轮回环代理测试覆盖真实 HTTP 服务：开启出网代理后，本机服务收到请求，
  代理服务收到 0 次请求。也覆盖 IPv4/IPv6 回环、误导主机名、私网策略保持。
- 既有真实双向 TLS 测试覆盖离线协调服务与缓存路由、候选并行尝试、查询限流、
  目录损坏后仍使用旧目录、大响应分块等。
- 2708 实机测试曾验证 Mac 从 Windows 读取 Range、MDK/Erika 播放与 seek。
  该次是单独视频链路测试，没有完成正常 UI 弹幕路径的验收。
- 此核查没有宣称已通过 Wi-Fi 切换、睡眠恢复、半开连接和长时播放的完整
  故障矩阵。自动穿透与中继不在产品要求或本轮改动中。
