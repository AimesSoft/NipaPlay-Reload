# NipaPlay Next：Agent 团队工作方式

> 从 M2 起所有任务书引用本文件。M1 任务书保留原有的严格约束。

## 分工

| 角色 | 负责 |
|---|---|
| 主控（架构） | 架构边界与模块间契约（Harness 公开 API、Action 语义、Effect 与授权）、跨模块一致性、产品与安全决策、环境与集成、端到端验收 |
| 实现者（Codex） | 在任务边界内的全部实现决策：内部结构、命名、文件拆分、私有 API、测试设计 |

主控不逐行审查代码：只检查架构契合度与契约兼容性，并运行验收。实现层面的问题发回实现者处理。

## 任务书写什么

- **目标**：交付什么结果，用户或 Agent 能因此做到什么。
- **边界**：可以改动的范围，以及不能触碰的东西。
- **对外契约**：其他模块、Agent 或 GUI 依赖的部分，例如 Action id、输入输出语义、公开类型。只有这些需要精确规定。
- **验收**：可执行的命令与可观察的行为。

内部设计不写进任务书，由实现者决定。

## 实现者的自主权与边界

- 规格之外的实现细节自行判断，并在报告的「决策」一节说明理由。
- 以下情况必须停下来提问，不能自行决定：
  - 改变公开契约或跨模块接口；
  - 改变用户可见的产品行为，或改变 Classic 模式的行为；
  - 涉及安全、凭据、权限；
  - 新增依赖或修改构建配置；
  - 需要修改任务边界以外的文件。

## 能力覆盖（始终有效）

- 用户能做到的，Agent 都应该能做到，权限相同，粒度对准意图：领域操作做成 Harness Action，设置项进入设置注册表，纯展示与导航用 `ui.*`。
- **新功能必须同时提供对应的 Action 或设置 schema。** 只做 GUI 的功能，要在报告中写明理由。
- 刻意不开放的只有两类：输入秘密，以及 Agent 给自己扩权。
- 覆盖率基线只升不降。

## 为 Agent 设计工具（始终有效）

- 遵守 DESIGN §2.3：提供可组合、支持批量的能力原语，不在代码里编排判断流程；代码只守不变量。
- 评价一组工具的标准是：Agent 能否用很少的调用、自然地组合出目标。如果 Agent 需要逐个操作、反复轮询或遵循说明书才能完成，说明工具设计有问题。

## 复用现有基础设施（始终有效）

- Next 层访问外部服务时，必须复用 Classic 现成的基础设施客户端，不得另写一套。尤其是弹弹play：一律经由 `NipaplayServerRouter`（香港与国内网关的主备选择与切换）与 `DandanplayHttpClient` 等现有客户端，经过我们自己的网关（路径前缀 `/dandanplay`，AppSecret 与签名在服务器上）。
- 拼接 URL 时，不要对带路径前缀的 base URL 使用 `Uri.resolve` 拼接绝对路径，它会丢掉前缀。

## 质量底线（始终有效）

- 不写防御性代码：不吞异常、不写“以防万一”的兜底、不对非空类型判空。外部输入在边界处校验，这属于正确性，不属于防御。
- 不做与任务无关的重构、格式化或重命名；不写变更说明式注释。
- 测试只测行为。
- 不提交、不 push、不运行 pub get。

## 环境

- Flutter 一律使用 CI 版本 3.44.6：`~/development/flutter-3.44.6/bin/flutter`、`.../bin/dart`。PATH 中默认的 3.47.2 编译不了本项目。
- analyze / test 一律加 `--no-pub`。
- 本机设置了 `HTTP_PROXY`：测试里访问回环地址的 `HttpClient` 要设置 `findProxy = (_) => 'DIRECT'`。

## 报告格式

1. 完成了什么；
2. 决策：自行做出的实现决策及理由；
3. 验收命令与真实输出；
4. 问题：需要主控决定的事项。
