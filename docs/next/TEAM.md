# NipaPlay Next：Agent 团队工作方式

> 所有任务书引用本文件。研究纲领见 `RESEARCH.md`，实验记录见 `EXPERIMENTS.md`。

## 分工

| 角色 | 负责 |
|---|---|
| 主控（架构） | 设计与它的演进、模块间契约、产品与安全决策、实验的选择与判读、真机实验、环境与集成 |
| 实现者（Codex） | 在任务边界内的全部实现决策：内部结构、命名、文件拆分、私有 API、测试设计 |

主控不逐行审查代码：只检查架构契合度与契约兼容性，并在真机上做实验。实现层面的问题发回实现者处理。

## 任务书写什么

- **目标**：交付什么结果，用户或 Agent 能因此做到什么。属于实验的，写明假设。
- **事实**：实现者需要知道、但从代码里看不出来的事。
- **实验**：要验证的假设，以及在真实环境中怎样观察。
- 只有别的模块、Agent 或 GUI 依赖的部分才需要精确规定。

内部设计、护栏清单、预设路线都不写进任务书，由实现者决定；没有真实需要时，不预先建造抽象、兼容层或护栏。

## 实现者的自主权与边界

- 规格之外的实现细节自行判断，并在报告的「决策」一节说明理由。
- 以下情况必须停下来提问，不能自行决定：
  - 改变 Classic 模式的行为（它有真实用户）；
  - 可能丢失或改写持久数据（任务、历史、绑定、回执、设置）；
  - 放松我们服务器上的限流与账号约束，或让秘密离开它所属的网站；
  - 新增依赖；
  - 需要修改任务目标以外的文件。

## 能力覆盖（始终有效）

- 应用的功能，用户能做到的，Agent 都应该能做到；反过来，用户不经 Agent 也能直接操作。
- **新功能同时提供对应的 Action 或设置 schema。** 只做 GUI 的功能，在报告中写明理由。
- 不开放给 Agent 的只有一类：替用户输入密码等登录秘密，登录由用户自己完成。

## 为 Agent 设计工具（始终有效）

- 遵守 `RESEARCH.md` 的不变假设：提供可组合、支持批量的能力原语，不在代码里编排判断流程；代码只守数据约束与基础设施，决定交给 Agent。
- 评价一组工具的标准是：Agent 能否用很少的调用、自然地组合出目标。如果 Agent 需要逐个操作、反复轮询或遵循说明书才能完成，说明工具设计有问题。

## 复用现有基础设施（始终有效）

- Next 层访问外部服务时，必须复用 Classic 现成的基础设施客户端，不得另写一套。尤其是弹弹play：一律经由 `NipaplayServerRouter`（香港与国内网关的主备选择与切换）与 `DandanplayHttpClient` 等现有客户端，经过我们自己的网关（路径前缀 `/dandanplay`，AppSecret 与签名在服务器上）。
- 拼接 URL 时，不要对带路径前缀的 base URL 使用 `Uri.resolve` 拼接绝对路径，它会丢掉前缀。

## 质量底线（始终有效）

- 不写防御性代码：不吞异常、不写“以防万一”的兜底、不对非空类型判空。外部输入在边界处校验，这属于正确性，不属于防御。
- 不做与任务无关的重构、格式化或重命名；不写变更说明式注释。
- 自动化测试只用来守住数据约束（绑定、回执、迁移不丢数据）和防止 Classic 退化，不用来证明功能成立。功能是否成立，由实验观察。
- 不提交、不 push、不运行 pub get。

## 环境

- Flutter 一律使用 CI 版本 3.44.6：`~/development/flutter-3.44.6/bin/flutter`、`.../bin/dart`。PATH 中默认的 3.47.2 编译不了本项目。
- analyze / test 一律加 `--no-pub`。
- 迭代时只跑受影响的测试文件；完整的 `flutter test --no-pub test/next`（另加改动涉及的 Classic 测试）只在报告前跑一次。数据库版本升级会让旧的迁移断言失败，所以最后那一次不能省。
- 多个同伴会同时工作，Flutter 测试一律排队、去掉代理再跑：`lockf -k /tmp/nipa-next/flutter-test.lock env -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY -u http_proxy -u https_proxy -u all_proxy NO_PROXY=127.0.0.1,localhost ~/development/flutter-3.44.6/bin/flutter test --no-pub <文件>`。测试宿主连不上导致的“加载失败”是环境问题，不是测试失败，不要因此重跑全量。
- 实验脚本写好后，改动只影响其中一部分时，只重跑那一部分。
- 实验配置下的 NipaPlay 默认是“安静”的：启动时放在其他窗口后面，不激活、不抢焦点。用户同时在用这台电脑，任何实验都不要激活窗口、移动鼠标或像素点击；截图用 `screencapture -x -o -l<窗口号>`。只有给用户演示时才用 `NIPAPLAY_LAB_QUIET=0`。
- 本机设置了 `HTTP_PROXY`：测试里访问回环地址的 `HttpClient` 要设置 `findProxy = (_) => 'DIRECT'`。

## 报告格式

1. 完成了什么；
2. 决策：自行做出的实现决策及理由；
3. 实验：做了什么，观察到什么（真实输出），包括意外和失败；
4. 问题：需要主控决定的事项。
