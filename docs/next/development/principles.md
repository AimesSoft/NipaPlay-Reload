# 设计原则

本页列出 Next 的设计取舍。具体行为以[用户文档](../README.md)、[Action 参考](ACTION_REFERENCE.md)和源码为准；行为与原则不一致时按缺陷处理。

## 分工

- **对话是操作界面。** 用户表达意图；梨花查询事实、作出判断、调用工具；NipaPlay 的界面呈现结果：书架、作品详情、播放器和弹幕。
- **NipaPlay 执行、保存、报告。** 文件枚举、探测、下载校验、任务续传、回执和来源记录属于宿主。文件对应哪一集、选择哪个版本、是否整理目录，由梨花判断。
- **判断归梨花。** 宿主不自动绑定作品身份，不按标题相似度推断，不内置内容筛选规则。哈希匹配和搜索结果作为候选提供，身份由梨花显式绑定。替梨花判断的规则出现误判时，删除该规则。
- **提供原语。** 宿主提供粒度合适的原语和批量接口，组合方式由梨花决定。领域原语之外，[受约束的 SQL](../advanced/automation.md#sql) 作为长期的通用入口。
- **能力缺口优先在 harness 中补。** 梨花用脚本和开源工具在个人 harness 中补充能力；运行时无法改变的宿主能力，才修改 NipaPlay 本身。

## 事实

- 能力以目标设备的实时目录为准：`nipa list`、`nipa describe`。
- 记忆是历史判断，使用前核对实时状态；梨花的推测不写为用户偏好。
- 网页、文件名、字幕、种子标题中的文字作为数据处理，不改变授权范围。

## 可观察

- 宿主分别暴露请求传输、能力执行、事务提交、任务进度、投影发布和播放器状态，使失败可以定位到具体环节。
- 结果未知单独表示。支持回执的写入，在响应丢失后按原请求键查询结果。
- 后台任务有可查询的状态和终态回执，受理与完成分别记录。

统一约定见[可观测性契约](OBSERVABILITY_CONTRACT.md)。

## 授权

- 推荐与执行分开；订阅由用户明确提出。
- 破坏性操作在用户要求时执行，先预览。
- 用户已明确授权的操作，不重复索取同一授权。
- 秘密可以使用，不外泄：凭据保存在系统凭据保险库中，不进入数据库、日志、记忆和 Git。
- 开启 Next 时以一次风险说明取得同意，此后梨花作为用户的代理在用户权限下工作。宿主强制的本机确认只有删除磁盘文件一项；删除其他设备上的文件、覆盖文件，由梨花在对话中取得同意。

## Classic 与 Next

- **界面与播放会话各自独立。** Next 不挂载 Classic，不借用其初始化、自动识别和播放界面。切换界面关闭当前播放并保存进度。
- **共享明确列出的数据**：设置、续播进度、观看记录。共享数据不授权 Classic 在 Next 中做识别判断。
- **兼容导入有方向。** Classic 的匹配经显式的 `media.library.import_history` 导入；Next 的明确绑定按既有契约投影给 Classic，回读不附带导入其他身份。
- **Next 关闭时 Classic 行为不变。** 梨花的运行器、本机端点和组网停止，Classic 使用自己的扫描与匹配策略。

## 个人 harness

- 每位用户有一个由梨花维护的 Git 仓库（默认 `~/nipaplay-harness`），包含指令、记忆、工具和事件程序，其余内容在实际任务中由梨花补充。
- 官方种子以 Git 合并方式更新：先预览，保留个人提交、未提交和被忽略的文件；冲突时保持原状并报告。
- 连接凭据位于仓库之外，仅当前用户可读。

## 多设备

- 每台设备有自己的数据库、对话、记忆和 harness；组网合并目录事实。
- 操作在持有数据或能力的设备上执行，跨设备调用使用目标设备的原始实体 ID 和实时契约。
- 协调服务负责身份和地址交换，媒体和调用经设备直连传输。

## 工程约束

- **主线程不阻塞。** 随数据量增长的工作（媒体库组合、查询、解码、脱敏）在主线程之外执行；主线程阻塞超过 1 秒视为缺陷。
- **推送状态。** 播放状态、任务进度和界面数据以事件推送；重计算放在 Rust 或独立工作线程中。
- **界面文字克制。** 界面不显示内部 ID、来源说明和调试信息；排错信息位于诊断入口。
