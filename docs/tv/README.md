# NipaPlay TV 知识库（Knowledge Base）

> 建立日期：2026-10-12 ｜ 维护责任：TV 端技术负责人
> 本知识库是 TV 端的**唯一事实来源**：版本规划、技术债、技能、版本记录、经验教训全部落这里，
> 任何开发前先查 `01-roadmap` 与 `02-tech-debt`，完成后**必须**更新 `04-version-log`。

## 1. 目录结构与用途

| 目录 | 用途 | 存放规范 | 维护时机 |
|---|---|---|---|
| `00-baseline/` | 项目基线报告（现状快照） | `YYYY-MM-DD-<主题>.md`，只追加不改写历史快照 | 结构性变化后 |
| `01-roadmap/` | 版本规划路线图 | 长期路线图 1 份 + 每版本 1 份计划 | 版本立项/调整时 |
| `02-tech-debt/` | 技术债登记册与评估模板 | 债务条目带 ID（TD-xxx）、状态、风险、拆解方案 | 开发前后各更新一次 |
| `03-skills/` | 可复用技能资产库 | 每技能 1 文件，必含**背景/方案/验证/适用场景** | 技能跑通当天 |
| `04-version-log/` | 版本记录与变更摘要 | `YYYY-MM-DD-<version>.md`，五段式：时间/内容/模块/技术债变化/技能沉淀 | **每次交付强制更新** |
| `05-lessons/` | 经验教训（含返工事故） | 按事故复盘格式：现象/根因/修复/预防 | 每次返工或线上问题 |

## 2. 强制流程（先规划 → 再开发 → 后沉淀）

1. **开发前**：在 `02-tech-debt/tech-debt-register.md` 完成风险评估——**未经评估的功能不得进入开发**。
2. **开发中**：达成里程碑即更新 `01-roadmap` 对应版本的进度，不等全部完成。
3. **交付后**（当天内）：
   - 更新 `04-version-log`（五段式变更摘要）；
   - 新学到的方案写入 `03-skills`（四要素齐全）；
   - 技术债变化（新增/减少/维持）更新到 `02-tech-debt` 登记册；
   - 返工/事故写入 `05-lessons`。
4. **同类问题第 3 次出现** → 升级为流程改进信号（在 `02-tech-debt` 建 TD 条目，要求流程级修复，不允许只记 lessons）。

## 3. 文档编写规范

- Markdown 标准格式；中文；表格/列表结构化呈现；
- 路径、命令必须**实测可复现**（禁止臆造 API、路径、版本号）；
- 不确定的推断统一标注 **`[待验证]`**，与事实严格分离；
- 引用本仓库其他文档用相对链接，外部链接给全 URL。

## 4. 与代码仓的关系

- 代码级重构报告（core/ui_common 抽取）仍在 `docs/refactor/`（历史归档，不再新增）；
- 本目录只放 **TV 端规划与知识资产**；
- 跨会话的高频上下文同时同步到会话记忆（memory 目录），两处指向保持一致。
